================================================================================
SERVER SPOT — TYPESCRIPT FULL-STACK REBUILD PROMPT
================================================================================

You are rebuilding ServerSpot from scratch as a production-grade, self-hosted
game server community platform. This document is the complete product and
engineering specification. Treat it as the source of truth.

ServerSpot is an all-in-one website + admin panel for game server networks
(Minecraft-first, multi-game capable). It combines:

  • A public storefront and community website
  • A polished admin dashboard
  • A custom Spot theme/templating system
  • Deep game-server and Discord integrations
  • Modular feature toggles (store, forum, support, blog, etc.)
  • Self-hosted-first deployment

Tagline direction:
  "Everything you need to run your game server website — store, community,
   support, and more."

The existing Rust/Dioxus prototype defines PRODUCT SURFACE and UX INTENT.
Your job is to implement it properly in TypeScript with real backend logic,
not mock admin UI only.

MONOREPO RULES
--------------
  • Domain logic lives in packages/*, NEVER deeply inside React components
  • apps/web orchestrates requests/UI; it does NOT own business rules
  • apps/worker and apps/game-gateway are first-class deployables
  • Import via workspace packages: @serverspot/store, @serverspot/forum, etc.
  • Avoid circular dependencies between packages
  • Shared UI only in packages/ui
  • Shared env/config only in packages/config
  • Shared auth/RBAC in packages/auth + packages/permissions
  • Spot engine in packages/spot
  • Do not turn packages/utils into a junk drawer

APP RESPONSIBILITIES
--------------------

apps/web
  • Main Next.js application
  • Public storefront/site (Spot-rendered for primary pages)
  • Admin dashboard (React + shadcn/ui)
  • API routes / server actions
  • Webhook endpoints: Stripe, PayPal, vote sites, Discord interactions
  • Auth routes via Better Auth
  • Upload/asset endpoints
  • Depends on domain packages; no duplicated business logic

apps/worker
  • Background processing service
  • Uses packages/jobs definitions
  • Handles: order fulfilment retries, email, webhook retries, scheduled
    publishing, analytics aggregation, cleanup, vote callback processing
  • PostgreSQL outbox/job table pattern initially
  • BullMQ + Redis swappable later without rewriting job contracts

apps/game-gateway
  • Persistent game-server connectivity service
  • Uses ws
  • Handles: authenticated connections, command delivery, player verification,
    account-link confirmation, server heartbeat, stat ingestion
  • Speaks through packages/game and packages/minecraft

apps/cli
  • Commander-based CLI
  • Commands: setup, doctor, migrate, seed, create-admin, backup, restore,
    theme:scaffold
  • Reuses domain services from packages

SECTION 3 — PRODUCT ARCHITECTURE
================================================================================

TWO DISTINCT APP SURFACES
-------------------------

1. PUBLIC SITE
   • Theme-driven via Spot templates (NOT hardcoded React for primary pages)
   • CSP-hardened
   • SEO-friendly SSR
   • Module routes only render when module is enabled
   • Configurable route aliases per module (/blog vs /news, /votes vs /vote)
   • Injected theme CSS variables from schema.json config
   • Controlled theme JavaScript runtime

2. ADMIN DASHBOARD
   • shadcn/ui polished admin shell
   • Sidebar + contextual subnav per module
   • Section/module accent colours
   • Dark-first, clean, flat surfaces — no gimmicky glows
   • Accent colour similar to #88d0f8 (ServerSpot light blue)
   • Fast filterable tables with nuqs URL state
   • React Query for interactive views
   • TipTap for rich content editing
   • Command palette optional but recommended

ARCHITECTURE LAYERS
-------------------
  Route/API layer (apps/web)
    → Service layer (packages/*)
      → Repository layer (packages/db)
        → PostgreSQL

  Background jobs (apps/worker)
    → Job handlers (packages/jobs)
      → Service layer (packages/*)

  Game connections (apps/game-gateway)
    → Game adapters (packages/game, packages/minecraft)

  Public rendering (apps/web)
    → Spot engine (packages/spot)
      → Theme pack files (themes/default/)

MODULE TOGGLE SYSTEM
--------------------
Every major feature is a module that can be enabled/disabled:
  store, forum, support, blog, players, leaderboards, votes, applications,
  analytics

When disabled:
  • Public routes return 404 or redirect
  • Admin nav hides module
  • API endpoints reject or hide module
  • Webhooks/events for that module pause

Store module settings in DB:
  • modules table (enabled flag)
  • global_settings / module_settings keyed by module
  • Preserve concept from original SurrealDB schema

SPOT SYNTAX
-----------
  {{ expr }}              Escaped interpolation
  {!! expr !!}            Raw HTML (must pass sanitization)
  @if (cond) ... @endif
  @elseif (cond)
  @else
  @foreach (collection as item) ... @endforeach
  @include('path/to/partial')

EXPRESSIONS
-----------
  • Dot paths: user.name, item.price
  • Literals: strings, numbers, booleans
  • not expr
  • config("option_id")        Read theme schema config value
  • display_url(config("discord_url"))   Sanitised URL output
  • Comparison: ==, !=, >, <, >=, <=
  • Logical: and, or
  • Filters/functions as needed (keep minimal in v1)

TEMPLATE CONTEXT
----------------
Server-side context objects passed per page, e.g.:
  site        { name, logo_url, favicon_url, ... }
  user        { id, name, avatar, roles, ... } or null
  config      Theme config values from schema
  items       Collection for list pages
  item        Single entity for detail pages
  boards, threads, products, tickets, etc.

Rendering pipeline:
  1. Load theme pack for active theme
  2. Resolve template file for route
  3. Build context from service layer
  4. Parse Spot → AST
  5. Render AST → HTML string
  6. Inject CSS variables from config
  7. Attach CSP headers
  8. Return SSR response

SCHEMA.JSON
-----------
Defines customizable theme options for admin visual config panel:

  {
    "options": [
      { "id": "accent_colour", "type": "colour", "label": "Accent colour",
        "default": "#88d0f8" },
      { "id": "hero_title", "type": "text", "label": "Hero title",
        "default": "Welcome" },
      { "id": "discord_url", "type": "link", "label": "Discord URL",
        "default": "" },
      { "id": "hero_background", "type": "image", "label": "Hero background",
        "default": "" }
    ]
  }

Option types: text, colour, image, link

Persist values in DB (theme_config_values table).
Inject as CSS custom properties:
  :root {
    --config-accent-colour: #88d0f8;
    ...
  }

Image uploads stored via packages/storage, served at controlled URL.

SECTION 22 — WORKING RULES FOR THE AI CODER
================================================================================

  1.  Build REAL backend/domain logic — not mock admin UI
  2.  Every module respects enable/disable settings
  3.  Every admin mutation must be authorised (RBAC)
  4.  Every external callback/webhook must be signature-verified
  5.  Every public-facing user content path must be sanitised
  6.  Spot theme system is a CORE feature, not an afterthought
  7.  Domain logic in packages/*, never in React components
  8.  Zod schemas shared between API, forms, and job payloads
  9.  Prefer boring, maintainable architecture over clever abstractions
  10. Strict TypeScript — no `any` unless documented
  11. Match ServerSpot product intent from this document
  12. Admin design: dark, clean, flat, #88d0f8 accent, no glows
  13. Public site: Spot-rendered, theme-configurable, CSP-hardened
  14. Self-hosted first — everything must work with docker-compose up
  15. Document as you build — README, .env.example, architecture docs
